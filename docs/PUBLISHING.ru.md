# Публикация Selectra

[English](PUBLISHING.md)

Selectra использует GitVersion 6.8.2 как источник числовой версии `X.Y.Z`. Текущий workflow публикует стабильные релизы по подходящим push в `main` и автоматически создаёт неизменяемый тег `vX.Y.Z`. Не создавайте и не перемещайте релизные теги вручную. Версия Fusion manifest внутри опубликованного ZIP и имя ZIP должны совпадать с GitVersion. Релизные файлы собирает и публикует только GitHub Actions.

## Проверки push и pull request

CI проверяет Python 3.14 на Ubuntu, macOS и Windows: компиляцию, модульные тесты, публичные метаданные и документы, манифест и ZIP. Сторонние Actions закреплены полными SHA коммитов; Dependabot предлагает обновления отдельными PR.

Каждая ОС загружает артефакт `Selectra-package-Linux`, `Selectra-package-macOS` или `Selectra-package-Windows` с ZIP и SHA-256. Workflow не запускает Fusion и не заменяет CAD-приёмку.

## Подготовка стабильного выпуска

1. Выполните CAD-сценарии на заявляемых платформах и запишите версии Fusion/ОС, выполненные проверки и ограничения в [протокол](VALIDATION.md). Различайте автоматические проверки и нативную приёмку.
2. Определите версию через GitVersion и обновите README, историю изменений и, где применимо, обе страницы `docs/releases/X.Y.Z.md` / `X.Y.Z.ru.md`. Сделайте реальные демо-снимки Fusion. CI подставляет GitVersion в манифест **внутри ZIP**, не меняя исходный файл репозитория.
3. Проверьте установку распакованного ZIP через интерфейс Fusion. Локальная сборка используется для проверки, а не для загрузки в Release.
4. Выполните локальные проверки и дождитесь успешного CI проверенного коммита, затем объедините его в `main`. Задание релиза запускается только при push в `main` с подходящими изменениями поставляемых файлов из `.github/release-paths.txt`. Push только документации может повторить ранее пропущенный выпуск с изменениями продукта, но сам по себе релиз не создаёт. PR и ручной запуск workflow не публикуют релиз.
5. После успешных заданий трёх ОС задание релиза скачивает все три пакета, проверяет манифест и SHA-256 и требует побайтового совпадения архивов. При наличии используются проверенные заметки конкретной версии; иначе общий Action создаёт заметки из истории Git.
6. `scripts/publish_release.py` создаёт черновик, загружает ZIP и контрольную сумму из CI, проверяет серверные дайджесты и публикует его. Текущий workflow использует стабильный канал и помечает релиз Latest. Токен GitHub Actions выдаётся только заданию публикации; скрипт отклоняет локальную публикацию.
7. Прочитайте опубликованные метаданные, скачайте ZIP и SHA-256 со страницы релиза, проверьте состав и контрольную сумму. Ссылка на CI и коммит включается в описание автоматически.

Архивы называются `Selectra-X.Y.Z.zip`. При несовпадении GitVersion, манифеста, байтов пакетов или контрольной суммы публикация блокируется. Опубликованный релиз неизменяем; повторные запуски не заменяют отличающиеся опубликованные файлы. Условия восстановления и выпуска приведены в [политике релизов](../.github/RELEASE_POLICY.ru.md).
